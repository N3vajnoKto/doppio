# Code Style — C++ (doppio)

За основу взят [стайлгайд ClickHouse](https://clickhouse.com/docs/ru/resources/develop-contribute/contribute/style)
и адаптирован под проект. Стиль нужен для единообразия: единообразный код проще читать и искать по нему.
Большая часть правил не имеет логического обоснования — они продиктованы практикой.

Правила автоматизированы:

- **Форматирование** — `clang-format` (конфиг `kit/.clang-format`, симлинк `.clang-format` в корне).
- **Именование и качество кода** — `clang-tidy` (конфиг `kit/.clang-tidy`, симлинк `.clang-tidy` в корне).
- CI (`.github/workflows/ci.yaml`) проверяет и то, и другое на clang 23; форматирование — в режиме `--Werror`.

## Отличия от ClickHouse

- **Скобки в стиле Java**: открывающая фигурная скобка на той же строке, закрывающая — на отдельной
  (у ClickHouse — Allman, скобки на отдельных строках). `else`/`catch`/`while` продолжают строку с `}`.
- **Указатели и ссылки прижаты к типу**: `const char* pos`, `int& counter`
  (у ClickHouse — пробелы с обеих сторон: `const char * pos`).
- Вместо типов-алиасов ClickHouse (`UInt8`, `Int64`, …) используем стандартные типы фиксированной ширины
  из `<cstdint>` (`uint8_t`, `int64_t`, …).
- Не применяются специфичные для ClickHouse пункты: библиотеки `DB/IO` и `DateLUT`, `contrib`-only
  зависимости, требования к платформе/компилятору (`clang` + `libc++`, `-Weverything`, статическая
  компоновка), написание названия продукта.

## Форматирование

Большую часть форматирования делает `clang-format` — не форматируйте вручную. Ключевые правила:

1. Отступ — **4 пробела**, без табов.
2. Длина строки — до **140** символов.
3. Открывающая скобка — на той же строке, закрывающая — на отдельной:

   ```cpp
   inline void readBoolText(bool& x, ReadBuffer& buf) {
       char tmp = '0';
       readChar(tmp, buf);
       x = tmp != '0';
   }
   ```

4. Если всё тело функции — один оператор, её можно записать в одну строку:

   ```cpp
   inline size_t mask() const { return buf_size() - 1; }
   ```

5. Пробелы **вокруг бинарных операторов** (`+`, `-`, `*`, `/`, `%`, …) и тернарного `?:`;
   пробел после запятой (и после `;` внутри `for`), но не перед ней.
6. **Без пробелов**: вокруг `.` и `->`, у унарных операторов (`++`, `--`, `*`, `&`, …), внутри `[]`.
7. Пробел перед `(` в `if`/`for`/`while` и т.п., но **не** в вызовах и объявлениях функций:

   ```cpp
   for (size_t i = 0; i < rows; i += granularity)
   void reinsert(const Value& x)
   memcpy(&buf[place_value], &x, sizeof(x));
   ```

8. В `template <...>` — пробел между `template` и `<`, без пробелов после `<` и перед `>`:

   ```cpp
   template <typename TKey, typename TValue>
   struct AggregatedStatElement {};
   ```

9. При переносе строки оператор переносится **на новую строку** с увеличенным отступом:

   ```cpp
   message << " ("
           << rows_read * 1000000000 / elapsed_ns << " rows/s., "
           << bytes_read * 1000.0 / elapsed_ns << " MB/s.) ";
   ```

10. Указатели и ссылки при объявлении прижимаются к типу: `const char* pos`, `int& counter`
    (не `const char * pos` и не `const char *pos`).
11. `const` пишется **перед типом**: `const std::string& s`, не `std::string const& s`.
12. `public`/`private`/`protected` — на уровне `class`/`struct`, члены — с отступом:

    ```cpp
    class MultiVersion {
    public:
        using Version = std::shared_ptr<const T>;
    };
    ```

13. Содержимое `namespace` **не смещается** отступом.
14. Если блок `if`/`for`/`while` состоит из одного оператора, фигурные скобки необязательны,
    оператор — на отдельной строке. Но если внутренний оператор содержит скобки или `else`,
    внешний блок обязательно в скобках:

    ```cpp
    for (auto& stream : streams)
        stream.second->finalize();
    ```

15. Не более одной пустой строки подряд; пустые строки разделяют логические блоки внутри функций
    и отделяют функции/классы друг от друга.
16. Одно выражение на строку; в конце строк нет пробелов; файлы в UTF-8 с LF и переводом строки в конце.
17. Используйте **префиксный** инкремент/декремент (`++i`), если постфиксная форма не нужна по смыслу.
18. Выравнивание пробелами внутри строки допустимо, но не обязательно.

## Именование

Все имена — на английском, без транслитерации. Сокращения допустимы, если общеупотребительны
(`AST`, `SQL`) или расшифрованы в комментарии рядом.

| Сущность | Стиль | Пример |
|---|---|---|
| Классы, структуры, union, enum | `CamelCase` | `Task`, `TaskDeletedError` |
| `using`-алиасы типов | `CamelCase` | `using FileStreams = ...` |
| Функции и методы | `camelCase` | `getName`, `addCounter` |
| Переменные, параметры, поля классов | `snake_case` | `max_block_size`, `handle` |
| Глобальные/статические константы, `#define` | `UPPER_CASE` | `MAX_TABLE_NAMES` |
| Значения `enum` | `CamelCase` (допустим `UPPER_CASE`) | `CompressionMethod::Lz4` |
| Параметры шаблонов | `T`, `U`, `T1`/`T2` или `TKey` | `template <typename TKey>` |
| Пространства имён | `lower_case` | `doppio` |

Дополнительно:

1. Поля классов — **без префиксов и суффиксов**: `handle`, не `m_handle` и не `handle_`.
   Локальные переменные и поля именуются одинаково.
2. Аргументы конструктора, которые только инициализируют поля, называются как поля **с `_` в конце**;
   суффикс можно опустить, если аргумент не используется в теле конструктора:

   ```cpp
   explicit Awaiter(std::coroutine_handle<Promise> handle_)
       : handle(handle_) {
       if (!handle_) {
           throw TaskDeletedError();
       }
   }
   ```

3. Абстрактные классы (интерфейсы) — с префиксом `I`: `IProcessor`. Других префиксов у интерфейсов нет.
4. Аббревиатуры: в переменных — строчными (`mysql_connection`), в классах и функциях — заглавными
   (`MySQLConnection`, не `MySqlConnection`).
5. Короткие имена допустимы только для локальных переменных с узкой областью видимости; остальные
   имена должны отражать смысл.
6. Нелокальные `enum` — только `enum class`.
7. Имена файлов повторяют содержимое: один класс — `CamelCase.h`, одна функция — `camelCase.cpp`.
   Заголовки — `.h`, исходники — `.cpp`.
8. Имена корутинных хуков (`await_ready`, `await_suspend`, `await_resume`, `get_return_object`,
   `unhandled_exception`, `initial_suspend`, `final_suspend`, `return_value`, `return_void`)
   фиксированы стандартом и остаются в `snake_case` — для них сделано исключение в `clang-tidy`.
   То же касается `promise_type`.

## Комментарии

1. Комментарии — **только на английском**.
2. Обязательно комментируйте все нетривиальные места. Комментарий часто помогает понять, что код
   не нужен или спроектирован неправильно.
3. Однострочные документирующие комментарии — `///`, многострочные — `/** ... */`.
   Обычные `//` — для пояснений и временного отключения кода.
4. Комментарий размещается **перед** кодом, к которому относится; изредка допустим в той же строке после кода.
5. В многострочных комментариях нет пустых строк в начале и конце.
6. Не добавляйте пустые шаблонные комментарии (author/date/purpose и т.п.) и бессмысленные шапки файлов.
7. Не используйте комментарии как разделители (`///******`), не пишите CAPS и не разводите дискуссии.
8. Не подписывайте закрывающие скобки блоков (`/// for`), кроме `namespace` — это делает clang-format.
9. Закомментированный код удаляйте перед коммитом.
10. Для библиотеки — подробное описание в основном заголовочном файле.

## Как писать код

### Ресурсы и память

1. **RAII**. Ручной `delete` — только в библиотечном коде и только в деструкторах.
   В прикладном кодом память освобождает владелец: стек, член класса, контейнер,
   `std::unique_ptr`/`std::shared_ptr` для кучи.
2. Анонимные блоки внутри функции допустимы, чтобы локализовать переменные и раньше вызвать деструкторы.

### Ошибки

3. Ошибки — через **исключения**. Обычно достаточно бросить исключение, не перехватывая (RAII всё освободит).
   В серверном коде перехват — на верхнем уровне обработчика; в функциях потоков исключения сохраняются
   и перебрасываются в главном потоке после `join`.
4. Никогда не глушите исключения: `catch (...) {}` — запрещено. Игнорируйте только конкретные случаи,
   остальное перебрасывайте (`throw;`).
5. Функции с кодами возврата/`errno` — всегда проверяйте результат и бросайте исключение при ошибке.
6. `assert` допустим для проверки инвариантов.
7. Исключения в деструкторах нежелательны: выносите опасную работу в `done()`/`finalize()`,
   вызываемые до разрушения объекта.

### Типы и значения

8. `const` — по умолчанию: константные ссылки, указатели на константу, `const_iterator`, `const`-методы.
   Не-`const` — только при необходимости. У передаваемых по значению аргументов `const` обычно бессмысленен.
9. Предпочитайте **ссылки** указателям.
10. Числа — типы фиксированной ширины из `<cstdint>` (`int32_t`, `uint64_t`, …), `size_t`, `ptrdiff_t`.
    Не используйте `long`, `long long`, `short`, `char` для чисел. `unsigned` — только когда действительно нужен.
11. Строки — `std::string` и `char*`, кодировка UTF-8. Никаких `std::wstring`/`wchar_t`.
12. Сложные шаблонные типы оформляйте `using`-алиасами (можно локально внутри функции):

    ```cpp
    using FileStreams = std::map<std::string, std::shared_ptr<Stream>>;
    FileStreams streams;
    ```

13. Не объявляйте несколько переменных разных типов в одном операторе (`int x, *y;` — нельзя).
14. Никаких C-style приведений — только `static_cast` и компания.
15. Инициализация: `std::string s = "Hello";` или `std::string s{"Hello"};`, но не `auto s = std::string{"Hello"};`.
16. Сложные значения передавайте по значению, если дальше они перемещаются (`std::move`);
    владение кучей — через `unique_ptr`/`shared_ptr` в аргументах.
17. Возврат — просто `return res;`, без `return std::move(res);`. Куча возвращается умными указателями.

### Классы и функции

18. **Rule of zero**: не пишите конструкторы копирования/перемещения, операторы присваивания и деструктор,
    если достаточно сгенерированных компилятором. `= default` допустим.
19. `virtual` — только если класс действительно полиморфный (это касается и деструктора).
    В базовом классе — `virtual`, в производных — `override` (без `virtual`).
20. Виртуальное наследование не используется.
21. Небольшие методы можно определять прямо в классе; у шаблонных классов объявление и реализация не разделяются.
22. Члены и методы группируются отдельно внутри каждой области видимости.
23. Конструктор по умолчанию не нужен, если для инициализации требуются аргументы. Отложенная инициализация —
    через `unique_ptr`/`shared_ptr` или явно описанный «невалидный» default-конструктор.
24. `trailing return type` (`auto f() -> void`) — только при необходимости.

### Прочее

25. `#pragma once` вместо include guards.
26. `using namespace` **запрещён** (проверяется clang-tidy). Конкретные `using` — локально, внутри класса или функции.
27. `namespace` — для средних и больших библиотек; в `.h` допустим `namespace detail`,
    в `.cpp` — `static` или анонимный namespace для сокрытия символов.
28. Никаких `iostreams`/`stringstream` в горячих циклах.
29. Многопоточность: сначала максимальная производительность на одном ядре, потом распараллеливание.
    Пул потоков вместо потока на задачу; синхронизация — `mutex` + `lock_guard`; без активного ожидания
    и без самописных lock-free структур, если это не ваша основная экспертиза.
30. Предпочитайте современный синтаксис: концепты и `requires` вместо `std::enable_if`,
    `contains` вместо `count`, `std::erase_if` вместо remove-erase, списочную инициализацию вместо `make_pair`.
31. Пишите как можно меньше кода и выбирайте самое простое решение. Неиспользуемый код удаляется.
32. Перед коммитом убирайте отладочный вывод и бессмысленные логи; логи — на английском, понятные
    администратору, без логирования в циклах.

## Специфика проекта

- Стандарт: **C++26** (`CMAKE_CXX_STANDARD 26`).
- Всё живёт в `namespace doppio`.
- Основа планировщика — корутины (`doppio::Task`); имена хуков корутин не переименовывать (см. «Именование»).
- Тесты — GoogleTest, лежат в `tests/unit/<модуль>/test_<имя>.cpp`.
- `size_t` без `std::` допустимо (как и `memcpy` без `std::`) — рекомендация ClickHouse для краткости.

## Инструменты и проверка

Конфиги лежат в сабмодуле `kit` и подключаются симлинками в корне (настраивается `kit/bin.sh init`).
CI использует clang 23; локально удобны `clang-format-23`/`clang-tidy-23`.

```bash
# отформатировать
clang-format-23 -i --style=file:kit/.clang-format src/scheduler/task.h

# проверить форматирование (как в CI)
find src tests -type f \( -name '*.cpp' -o -name '*.h' \) -print0 \
  | xargs -0 clang-format-23 --dry-run --Werror --style=file:kit/.clang-format

# статический анализ (нужен compile_commands.json)
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
clang-tidy-23 -p build --config-file=kit/.clang-tidy tests/unit/scheduler/test_task.cpp

# сборка и тесты
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Подавление проверок (`NOLINT`/`NOLINTNEXTLINE`) допустимо только точечно и с пояснением причины
в комментарии рядом.
